# Fixing GitHub Connection Timeouts by Switching HTTP/2 to HTTP/1.1

## Problem Background

While running `git push` to GitHub, a connection timeout occurred:

```bash
fatal: unable to access 'https://github.com/chenbin98/meteo_data_download.git/':
Failed to connect to github.com port 443 after 75003 ms: Couldn't connect to server
```

The connection failed after approximately 75 seconds, so the code could not be pushed. This problem can occur in some network environments, particularly when GitHub is accessed over HTTPS.

## Diagnosis

### 1. Check Basic Network Connectivity

First verify that the network itself is available.

```bash
# Test whether GitHub is reachable
curl -I https://github.com

# Check DNS resolution
ping -c 2 github.com
```

**Result:** the network path and DNS resolution were functioning, so this was not a basic connectivity failure.

### 2. Check Git Configuration

Check for proxy settings or other Git configuration issues:

```bash
# Check proxy settings
git config --global --get http.proxy
git config --global --get https.proxy

# Check SSL verification
git config --global --get http.sslVerify
```

**Result:** no proxy was configured and SSL verification was enabled by default.

### 3. Inspect the Git Connection in Detail

Use verbose logging to inspect the failure:

```bash
GIT_CURL_VERBOSE=1 git ls-remote origin 2>&1 | tail -30
```

**Key observations:**

- SSL certificate verification succeeded.
- The connection was established, but timed out after the request was sent.
- The diagnostic output included `Error in the HTTP/2 framing layer`.

**Conclusion:** the problem occurred at the HTTP/2 protocol layer. GitHub HTTP/2 traffic can be unstable in some network environments.

## Solutions

### Option 1: Disable HTTP/2 and Use HTTP/1.1

Git commonly uses HTTP/2. Forcing HTTP/1.1 can improve compatibility.

```bash
# 1. Force Git to use HTTP/1.1 globally
git config --global http.version HTTP/1.1

# 2. Increase the buffer for large pushes
git config --global http.postBuffer 524288000

# 3. Disable low-speed limits to avoid interrupting slow connections
git config --global http.lowSpeedLimit 0
git config --global http.lowSpeedTime 9999

# 4. Push again
git push --set-upstream origin main
```

**Why this helps:**

- `http.version HTTP/1.1` forces HTTP/1.1 and avoids HTTP/2 compatibility issues.
- `http.postBuffer 524288000` configures a 500 MB buffer for large pushes.
- `http.lowSpeedLimit 0` disables the low-speed cutoff that can interrupt a slow connection.

In this case, the push succeeded after applying these settings.

### Option 2: Configure a Proxy

If an authorized local proxy is already available, Git can use it for the connection.

```bash
# Identify the proxy port; common values include 7890, 1087, and 6153

# Set Git proxy values
git config --global http.proxy http://127.0.0.1:7890
git config --global https.proxy http://127.0.0.1:7890

# Push
git push --set-upstream origin main

# Remove proxy values when no longer needed
git config --global --unset http.proxy
git config --global --unset https.proxy
```

### Option 3: Use SSH for Long-Term Use

SSH is often more stable than HTTPS and does not require repeatedly entering credentials after setup.

```bash
# 1. View an existing SSH public key
cat ~/.ssh/id_ed25519.pub

# 2. Generate a key if one does not exist
ssh-keygen -t ed25519 -C "your_email@example.com"

# 3. Add the public key to GitHub
# Visit https://github.com/settings/keys and select "New SSH key"

# 4. Test SSH connectivity
ssh -T git@github.com

# 5. Switch the remote to SSH
git remote set-url origin git@github.com:chenbin98/meteo_data_download.git

# 6. Push
git push --set-upstream origin main
```

**Advantages:**

- No repeated password entry.
- More stable connectivity.
- No dependence on HTTPS proxy behavior.

## Troubleshooting Flow

```text
git push fails
    │
    ▼
Check network: curl/ping github.com
    │
    ├── unreachable → check network or proxy
    │
    ▼ reachable
Check Git configuration: git config --get http.proxy
    │
    ├── proxy present → confirm it is correct
    │
    ▼ no proxy
Detailed diagnostic: GIT_CURL_VERBOSE=1 git ls-remote origin
    │
    ├── SSL failure → check certificate or system time
    ├── HTTP/2 error → switch to HTTP/1.1
    └── authentication failure → check credentials or SSH keys
```

## Comparison of Options

| Option | Strength | Limitation | Best use |
| --- | --- | --- | --- |
| **HTTP/1.1** | Simple and immediate | HTTPS authentication may still be required | Short-term repair |
| **Proxy** | Reaches blocked resources | Depends on local proxy stability | Environments with an authorized proxy |
| **SSH** | Stable and credential-friendly | Requires SSH-key setup | Recommended for long-term use |

## Summary

The central repair commands are:

```bash
git config --global http.version HTTP/1.1
git config --global http.postBuffer 524288000
git config --global http.lowSpeedLimit 0
git config --global http.lowSpeedTime 9999
git push --set-upstream origin main
```

For long-term work, configure an SSH key and switch the remote to SSH for a more stable connection experience.
